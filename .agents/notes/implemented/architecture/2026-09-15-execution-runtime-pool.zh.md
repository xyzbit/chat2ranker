# Agent Note: 持久化 Sandbox 资源准入

Status: implemented

[English](2026-09-15-execution-runtime-pool.md) | 中文

## 问题

增加 Worker 消费者不会增加独立 Sandbox 宿主机的 CPU 或内存。模型与租户额度可能让许多不同调用方同时进入同一宿主机，而 Worker 丢失后，业务结果已经失败，分配的运行时仍可能存活。

## 决策

Execution 为一个 OpenSandbox 服务及拥有范围保存运维分配的资源池。资源池包含独占的 CPU/内存预算；消耗该预算的所有分配方必须共享同一 Execution 数据库。同一数据库中的一个端点只有一个资源池。这是对已分配预算的预留，不是主机发现，也不代表拥有其他应用正在使用的资源。

准入时冻结 `runtimePlan`：资源池、服务 URL、范围、镜像及整数毫核/字节限制。公共请求不能提供这些字段。幂等重提返回原计划。目标或镜像不同的 Worker 延后执行，不修改请求；修改单容器默认值不会改变排队任务的限制。缺失计划在分配前失败，超过预算的请求在准入时拒绝。后续降低预算会保留已有分配，并让不再适配的工作继续排队。

将尝试标记为运行前，Repository 在记录运行事件及检查模型/租户额度的同一事务中检查剩余 CPU 和内存。PostgreSQL 跨 Worker 串行化准入，SQLite 串行化本地数据库写入。运行中、取消中及终态待清理尝试保留冻结的资源预留。未知旧分配会保守地阻止新的预留。只有确认清理后才解除义务，终态结果发布仍是独立事实。租约过期或 Worker 数量变化不会释放未知分配。

资源池配置持久化保存。启动时创建不存在的资源池，或核对配置完全一致。`-configure-sandbox-pool` 显式更新预算后退出；运行中的 Worker 在每次准入时读取该权威预算。修改服务/范围必须先排空所有排队、活跃及未确认工作。运维修改持久预算后，需要同步更新 API/Worker 的启动参数。PostgreSQL schema 6 使用显式维护迁移，SQLite 记录 schema 10。

容量接口在同一个一致事务快照中读取计划、预留和资源池预算，跨在线/评测队列虚拟分配剩余资源，并将 `resourceBlocked` 与模型/租户 `quotaBlocked` 分开报告。资源阻塞的工作不会增加可执行 Worker 需求。只有匹配当前目标/镜像的尝试才增加活跃 Worker 需求；其他镜像仍保留其共享资源预留。聚合指标不返回资源池 ID 或服务位置。

## 考虑过的替代方案

**将 Worker 副本数视为宿主机容量。** Worker 控制远程容器，其副本数无法限制这些容器消耗的资源。

**使用进程内信号量。** 每个 Worker 都会接受自己的最大值，进程丢失还会在容器仍运行时丢弃预留。

**建立宿主机调度器和资源租约。** 一个明确分配的服务预算不需要节点注册、放置算法或第二个生命周期管理器。持久化 Execution 尝试已经拥有分配与清理职责。

## 后果

CPU 和内存可分别阻塞不同模型、不同租户的准入。真实 SQLite/PostgreSQL 测试覆盖并发启动、未知结果预留、显式预算更新、目标变更拒绝和冻结计划读取。Executor 测试检查配置变更后实际创建请求的资源限制。[实验验证器](../../../../rank/deploy/k8s/verify-runtime-pool.py)将两个 Worker 与真实 DSH 容器的行为对照组装应用快照，并恢复原预算。

运维必须为内核、守护进程和其他负载预留余量，并避免独立数据库或直接生命周期客户端重复使用同一预算。资源池配置不执行磁盘、出口或主机级隔离，不创建机器，也不发现实际空闲资源。多物理主机及服务端准入仍属于[提案](../../proposed/architecture/2026-09-14-rank-production-execution.md)中的独立生产验收工作。
