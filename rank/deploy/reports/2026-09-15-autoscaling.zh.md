# Execution 自动扩缩容实验 — 2026-09-15

[English](2026-09-15-autoscaling.md) | 中文

[机器可读报告](2026-09-15-autoscaling.json)记录了有界 KEDA 验证的成功结果及此前的失败。[可重复运行的脚本](../k8s/verify-autoscaling.py)使用打包的 Execution API/Worker Pod、PostgreSQL/River、独立 OpenSandbox 容器内的真实 DSH 进程，以及响应延迟十秒的确定性模型。全部服务运行在一台笔记本上。minikube profile 请求四个 CPU 和 4 GiB，Kubernetes 报告的 allocatable 为八个 CPU 和 8,025,700 KiB；二者均不能证明独立物理容量。远程 Sandbox 容器不受 Kubernetes 调度，因此增加 Worker 不会增加 Docker 宿主机。

| 阶段 | 实测结果 |
| --- | --- |
| 16 个负载请求，模型并发额度四 | 16 个全部在第一次尝试完成；就绪 Worker 从一个增加到三个。 |
| 排空 | 可执行需求归零后，期望与就绪 Worker 从三个回到一个。 |
| 模型并发额度一，八个请求 | 40 秒观察期内，虽然有额度阻塞的工作，需求始终不超过一、Worker 始终为一个。两个请求完成；随后取消六个。 |
| 清理与恢复 | 提交的运行时没有遗留待清理记录。临时模型已移除；API/Worker 额度恢复为四，实验 scaler/HPA 已移除，两个手动管理的 Worker 就绪。 |
| 代理网络 | 检查运行中的 Sandbox 未发现宿主机端口映射；远程执行通过服务端鉴权代理完成。 |

16 个突发请求从创建到开始执行的排队时间为 p50 **53.30 秒**、p95/最大值 **107.75 秒**，包含运行时创建、刻意延迟的模型和从一个 Worker 逐步扩容的影响。本实验验证有界扩缩容与任务结果可核对，不代表达到或定义了聊天交互时延目标。生产决策仍需要按到达率施压、测量预热容量和真实模型预算。

此前一轮有 14 个请求完成、两个失败：OpenSandbox 0.2.3 选择了 Docker 已绑定的宿主机端口，因为分配器探测的是生命周期服务所在容器的网络命名空间。实验采用[检查版本的构建补丁](../k8s/opensandbox-proxy-only.py)，关闭不需要的宿主机端口映射。Docker 创建/销毁事件中的精确 execution/attempt/scope 标签为经审计的人工修复提供两个丢失句柄；普通协调器确认运行时不存在后释放清理预留。两个失败结果仍保留为失败，没有重放调用。成功重跑使用的补丁服务镜像记录在报告中。

补丁服务上的完整平台回归也通过：网关鉴权、每日热点请求、多轮 OpenAI SDK 聊天、Agent 试用、中控会话持久化、S3/SSE 读取、Rank/control Pod 替换，以及 Worker 从零恢复为两个。恢复后的排队请求在第一次尝试完成。

本轮覆盖在线需求、应用并发额度、空闲排空及有限取消，不证明供应商 RPM/TPM 处理、评测池性能、所有拥有权切换时刻的中断处理、生产鉴权、磁盘/出口隔离、物理主机扩容或高可用。部署步骤见[实验教程](../k8s/README.md)，指标语义见[容量决策](../../../.agents/notes/implemented/architecture/2026-09-15-execution-capacity.md)。
